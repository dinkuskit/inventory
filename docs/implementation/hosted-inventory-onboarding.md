# Hosted Inventory onboarding

The account control plane records site connections and Inventory operation
identities. Stock remains authoritative in the existing SQLite-backed
`InventoryPool` kernel. It never creates a Commerce ledger.

`POST /v1/connect` accepts a frozen `create` request (first location name), or
an explicit `reconnect` request (owned operation ID). The signed account subject
selects the account object; signed `site_id` selects the site binding. Browser
account, principal and pool fields are rejected. `GET /v1/status`,
`GET /v1/operations` and `GET /v1/locations` use the same authorization boundary.

Operation/pool identity is durable before location provisioning. Unknown
outcomes remain pending and retry the original `location.create` command.
The command's originating site is frozen, including when a second site
reconnects during pending provisioning. Terminal kernel rejection is recorded
as failed. Retry cannot replace inventory or alter a terminal result.

The sandbox plugin uses Block Kit, a private `plugins:manage` route with
host-attested `routeCtx.user`, capability-declared HTTP, and encrypted host
settings for the PKCE verifier. Connect uses the store-control challenge and
public proof receipt in [store-connect](store-connect.md). Website Better Auth
owns merchant consent and token issuance; this repository only proposes that
wire format. A persisted connection intent still protects Inventory
provisioning from browser/network retries. Stock receiving and adjustment
screens are outside this setup slice.

## Integration boundary

The website half-contract is present at the Better Auth counterpart
`.grilltrack/work/better-auth/CONTRACT.md`. It agrees on account key, JWT
claims, and refusal of caller-supplied site identity. It still fail-closes
merchant-session `POST /account/tokens` and has not adopted the plugin
back-channel (`POST /api/store-connections`, `POST /api/store-connections/token`,
public store-proof fetch, or start `expires_at`). Inventory does not call
`/account/tokens`. The service must be configured by DinkusKit with HTTPS
issuer/JWKS URLs and audience. Tokens must bind the authenticated issuer
subject, approved site grant, `inventory:admin` scope and expiry. A posted
plugin `site_id` is not site proof. Real authentication, consent, account
creation and renewal remain unproven.

Service/account origins and publisher in the plugin manifest deliberately use
reserved `.invalid` names. They are fail-closed placeholders, not functioning
production endpoints or a verified publisher. DinkusKit must configure these
through a separately approved service/account setup; shop owners do not enter
infrastructure details. Without issuer configuration the hosted Worker returns
`account_service_unconfigured` with HTTP 503.

## Proof

The exact scaffold/runtime pin is `emdash@1.0.1`, Block Kit `1.0.1`,
plugin CLI `0.13.1`, workerd sandbox runner `0.9.1`, JOSE `6.2.12`.
The service keeps compatibility date `2026-08-28` because the pinned local
workerd binary does not support today's date. This is a local runtime limit.

Run `bin/verify-inventory quick|full`; focused checks are `npm run test:hosted`,
`npm run typecheck:plugin`, `npm run build:plugin` and `npm run bundle:plugin`.
`node tools/run-hosted-onboarding-proof.mjs` detects a Node 24 executable
read-only and runs the disposable local EmDash dispatcher/sandbox host with
local SQLite Durable Objects. Website/account identity is a labeled synthetic
transport, not live Better Auth. `--serve` opens http://127.0.0.1:4329 using
the published Block Kit renderer. The host supplies the config and environment
constants normally generated by Astro; it is not a complete Astro site or a
signed Registry install. The standalone host still needs Node 24 for
`registerHooks`; the wrapper does not rewrite the runtime to fake sandbox
success.

The full verifier and hosted Worker dry run pass. The standalone sandbox proof
passes setup, unknown-response retry, frozen intent, reinstall, owned reconnect,
foreign-account refusal/recovery and private-route authorization. Browser proof
shows the connected location using the actual published Block Kit renderer.
See [local proof](../../.grilltrack/proof/hosted-onboarding/PROOF.md).

The harness supplies synthetic public DNS answers only for its two reserved
proof names so the host SSRF guard can validate them; its HTTP transport stays
local and allowed-host enforcement remains enabled. Real DNS/endpoint access,
identity, consent and remote provisioning are not proven by this fixture.
Formal review is pending. No publication, deployment, production mutation,
merge or clean review is claimed.
